# xUDT Studio

A small dashboard built after finishing the
[Create a Fungible Token](https://docs.nervos.org/docs/dapp/create-token) tutorial,
to put what it teaches into one coherent app instead of three disconnected forms.

The tutorial example asks you to paste an xUDT args string into every step. This one
starts from an account and works outward: what do I hold, what can I issue, where did
my tokens go.

```
┌──────────────────────────────────────────────────────┐
│ xUDT Studio  [devnet]                    block #27k  │
│ Account #0 ckt1qzda…cytcyd8                          │
│ 41,464,655 CKB · 1 token held · lock 0x7de82d61…     │
├──────────────────────────────────────────────────────┤
│ holdings │ issue │ transfer │ explore                │
├──────────────────────────────────────────────────────┤
│ TOKEN (xUDT ARGS)        AMOUNT  CELLS   CAPACITY    │
│ 0x7de82d61a7…5300000000      96      1    146 CKB    │
└──────────────────────────────────────────────────────┘
```

## Run it

```powershell
offckb node                          # devnet, in another terminal
npm install
npm run accounts                     # regenerate src/accounts.ts from offckb
$env:NETWORK='devnet'; npm start     # bash: NETWORK=devnet npm start
```

Then open http://localhost:1235 (the tutorial example uses 1234, so both can run
side by side).

```powershell
npm run lint    # tsc --noEmit
npm run smoke   # runs the domain layer against the live devnet
```

## How it is put together

| File | Responsibility |
|---|---|
| `src/ckb.ts` | Every chain interaction: query, issue, transfer, capacity maths. No React. |
| `src/index.tsx` | UI only — tabs, forms, tables. Never touches the RPC directly. |
| `src/client.ts` | Network selection and the devnet's deployed script config. |
| `src/accounts.ts` | Generated by `npm run accounts`. Addresses only, never private keys. |
| `scripts/smoke-test.js` | Compiles `ckb.ts` and asserts against a running devnet. |

Keeping the chain logic free of React is what makes `npm run smoke` possible: the test
and the browser run the same functions, so a passing test says something real about the
app. Output against my devnet:

## What it does differently

Each of these is a problem I hit while following the tutorial (see the
[main README](../README.md) for the full list):

- **Args that explain themselves.** Paste a 32-byte lock script hash — what the
  tutorial's recap tells you to query with — and the app appends the 4-byte flags
  field and tells you it did, instead of an alert saying "not found".
- **Capacity measured, not guessed.** The Issue tab computes what a token cell costs
  from the actual lock and type scripts (146 CKB here) rather than the example's
  hard-coded 61, which is the floor for a bare cell and lets you start a transaction
  that cannot succeed.
- **Integers enforced.** `1.5` is rejected with a reason; the tutorial's number input
  accepts it and throws `Cannot convert 1.5 to a BigInt` from deep inside the SDK.
- **Holdings by account.** One indexer query with a type-script filter finds every
  xUDT an account holds, so you never need to know a token's id in advance.
- **Keys are never stored on disk.** The generator writes addresses only; a signing
  key lives in `sessionStorage` for the tab's lifetime. Nothing secret can reach a commit.
- **Devnet is the default.** The tutorial's client silently falls back to testnet when
  `NETWORK` is unset, which on Windows happens every time, since `NETWORK=devnet npm
  start` is not valid in PowerShell or cmd.

## What it shows about the cell model

The Explore tab is the point of the whole thing. Query a token and you see it as the
chain does: a list of cells, each with its own amount and its own lock script. Two cells
of 10 under the same lock are not merged into 20 anywhere — the "balance" is a sum the
UI computes. Sending tokens replaces a lock script; the tokens never move.
